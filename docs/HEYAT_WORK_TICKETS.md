> 版本：1.0（执行 Backlog）  
> 日期：2026-10-22

## 0. 已确定范围、默认假设及不可违反约束

**目标：** 一款以精致半写实酒店剖面（此前选中的图三）为视觉基准的短流程主动增量游戏；网页优先，Three.js + WebGL 2；从一间房成长为一栋持续自动运转的 HEYAT 酒店；V0.1 时长 20–30 分钟。

**先执行的默认假设（非用户最终确认）：** 横屏主体验、竖屏基本可玩；不做离线收益、广告、内购和多酒店；以 iPhone 12/13 级设备 Safari 为目标移动测试层级，实际设备型号待用户确认。正式发行名称与商标风险需独立审核，HEYAT 目前为项目工作名。

**技术底线：**

- `TypeScript + Vite + Three.js WebGLRenderer`，默认走 WebGL 2；运行时依赖本地打包，不靠 UNPKG/CDN 唯一加载 Three.js。
- 经营模拟器、渲染、UI、存档完全分层；Three.js 动画不得修改资金、订单或房态。
- 模拟器固定步长 / 确定性时钟；所有现金变化通过唯一订单结算入口，禁止二次结算。
- 主动增量体验：0–5 分钟解锁第一项关键自动化、15–20 分钟出现明显扩建，最终数值节奏以实际测试为准。
- 角色使用近中远三级表示；房间照明以烘焙与廉价视觉假象为主；渲染角色数量不等于模拟客人数。
- 不依赖旧 GitHub Pages 压缩 bundle 作为源码，不直接抄袭现有酒店品牌素材与标识。
- **真实性原则：** Work 云端浏览器的桌面测试不能代替 iPhone Safari 实机性能。没有真机数据时必须标记 `MOBILE_PERF_UNVERIFIED`，不得声称达成 30 FPS。
- 第一次初始化空仓库可以进行必要的 `main` 首个 bootstrap commit；后续所有变更一律独立分支 + PR，**不自动合并 PR**。

## 批次 A — 项目与依据

### HYA-001 — 初始化 HEYAT 可维护工程（P0 / S）

**依赖：** 无；最先执行。  
**范围：**
- 检查 `GarronMeng/HEYAT` 内容、默认分支和已有权限；如仍为空，执行最小 bootstrap commit，随后按 feature branch/PR 工作。
- 建立 Vite + TypeScript + Three.js 工程，Node 版本文件、锁文件、README、`.gitignore`、ESLint/Prettier（或等效统一规范）、Vitest、CI 工作流。
- 将现有 `HEYAT_GAME_VISION.md` 和 `HEYAT_DEVELOPMENT_PLAN.md` 放入 `docs/`，将本 backlog 放入 `docs/`。
- 页面具有加载提示、初始化失败提示，页面包含真实 canvas，启动依赖从构建产物加载；不从 UNPKG 直接 import。
- 设置本地 `npm run dev / build / test / typecheck / lint`（具体命令按 package.json）。

**验收（DoD）：** 克隆、安装、开发预览、构建、测试与类型检查全成功；GitHub Actions 执行构建检查；README 提供完整复现步骤；有可访问的构建截图与 PR 说明。  
**不做：** 经营逻辑、完整酒店、后端、多平台登录。  
**建议分支：** `chore/heyat-bootstrap`。

### HYA-019 — 旧《今晚有套吗？》源码及资源只读审计（P1 / S，可与其他任务并行）

**依赖：** 无。  
**范围：**

**验收：** 形成可核查的引用路径及复用建议；不对旧仓库和 HEYAT 主分支做修改；不将 minified JS 当作源文件。  
**不做：** 迁移旧项目全部代码、复制现实酒店品牌受保护素材。

## 批次 B — WebGL 视觉及性能可行性

### HYA-002 — 图三基准场景的轻量 WebGL Demo（P0 / M）

**依赖：** HYA-001。  
**范围：**
- 使用 Three.js 制作「一层大堂 + 两间客房 + 六名小型活动角色」可运行场景，原创 HEYAT 招牌。
- 风格：深夜蓝外景 + 暖金客房/大堂 + 黄铜/玻璃点缀，比例写实但模型简化；相机 3/4 剖面视角，限制旋转，支持缩放。
- 客房家具模块化、共享几何材质；静态烘焙或廉价替代灯光；角色采用简易移动/循环动画并具备后续 LOD 扩展点。
- 窗口缩放、屏幕旋转时画面正常；资源加载失败时可重试、不会永久黑屏。

**验收：** 桌面 Chrome 中实际 WebGL 渲染并可拖拽/缩放，角色确实在运动；提供场景截图和工程资产统计；视频或动态录屏证明不是静态概念图。  
**不做：** 大型豪华酒店模型、完整人物表情/骨骼、实时全楼阴影、完整经营 UI。  
**建议分支：** `feat/benchmark-diorama`。

### HYA-003 — FPS/帧时间/Draw Call 面板与画质分档（P0 / S）

**依赖：** HYA-002 画面可运行。  
**范围：**
- 开发环境显示 FPS、帧时间 P50/P95、Draw Calls、可见三角形/对象数、内部分辨率与画质档。
- 实装 Low/Medium/High 切换：像素比限制、人物密度、阴影/特效、背景复杂度，确保功能与状态不受画质影响。
- 提供至少 2 分钟桌面自动采样脚本或页面导出数据功能；记录浏览器、分辨率、机型、档位、采样时长。
- 增加 `webglcontextlost` 等异常可恢复处理；准备 iPhone Safari **人工实机操作步骤**与数据收集模板。

**验收：** 画质切换前后视觉不同、经营逻辑不变；可导出性能 JSON/CSV；报告清晰区分已验证桌面结果与 `MOBILE_PERF_UNVERIFIED`。  
**不做：** 以模拟器/桌面设备宣称 iPhone 30 FPS 实机合格。  
**建议分支：** `perf/benchmark-tooling`。

## 批次 C — 确定性经营逻辑

### HYA-004 — 单一 GameState + 房态状态机（P0 / M）

**依赖：** HYA-001。  
**范围：**
- 定义 GameState/schema、固定时间步与事件、可复现随机数/seed；接口独立于 Three.js。
- 房态：`LOCKED → AVAILABLE → RESERVED → OCCUPIED → DIRTY → CLEANING → AVAILABLE`。
- 明确建房、分房、清洁的前置条件，禁止负数容量与两个订单共用一间客房。
- 实现命令/Reducer；引入严格的类型及测试。

**验收：** 单元测试覆盖合法/非法转换、重复点击、边界时间、空房不足与多订单竞争；同 seed + 同命令列表产出相同状态。  
**不做：** 把业务逻辑写入 Three.js `animate()`。

### HYA-005 — 客流、前台、订单、退房和收入结算（P0 / M）

**依赖：** HYA-004。  
**范围：**
- 客人需求生成、排队（容量上限）、接待速度、房型分配、入住持续时间、离店与清洁需求。
- 使用唯一订单 ID 和幂等结算事件，保证每次订单仅结算一次；保留收入流水与汇总。
- 在无 3D 的 debug 面板展示模拟客流、房态和现金；和渲染彻底解耦。

**验收：** 连续模拟 10,000+ 事件后无负现金、无重复结算、无单房双订单、无队列无限增长；事件日志可按种子重放。  
**不做：** 员工薪资、贷款、真实酒店 PMS 接口。

## 批次 D — 增量玩法

### HYA-006 — 数据驱动的 12 项升级与前置解锁（P0 / M）

**依赖：** HYA-005。  
**范围：** 参照 `HEYAT_GAME_VISION.md` 实现收益 4 / 效率 4 / 规模 4 项升级；每项定义价格曲线、等级上限、效果类型、前置条件、3D 反馈事件，提供推荐升级接口。  
**验收：** 余额不足不购买、不重复扣款；每个升级前后指标可算；自动入住、自动清洁能真正改变模拟行为。  
**不做：** 仅修改屏幕显示数字的假升级。

### HYA-007 — 批量经济模拟器和成长节奏调参（P0 / M）

**依赖：** HYA-005、HYA-006。  
**范围：** 创建命令行模拟器：不同种子和升级购买策略跑 30 分钟游戏，输出 CSV/JSON 曲线与里程碑时刻；检测瓶颈、死锁、NaN/Infinity、不可达升级和 >90 秒无可操作决策区间。  
**验收：** 至少三种购买策略跑通；自动化首次出现目标 3–5 分钟，扩建目标 15–20 分钟，终局 20–30 分钟；超标区间有清楚的调参报告。  
**不做：** 无数据依据硬说“游戏已足够上瘾”。

### HYA-008 — 本地存档、版本迁移与时间恢复（P0 / S）

**依赖：** HYA-004、HYA-005。  
**范围：** IndexedDB 或经论证的 localStorage、存档 schema version、自动保存、导入/导出 debug 快照、错误恢复、页面回前台时的时钟规则。  
**验收：** 关闭/刷新不丢关键状态；存读档不会补算不存在的离线收益、不会重复订单结算；旧版存档模拟迁移成功或明确拒绝。  
**不做：** 云存档、账号系统。

### HYA-009 — 主动操作、自动化与建筑扩张规则（P0 / M）

**依赖：** HYA-006、HYA-007。  
**范围：** 手动接待/启动清洁、自动前台/自动清洁切换、升级购买影响实际吞吐；建房与解锁楼层规则、阶段目标与状态事件。  
**验收：** 玩家能从手动经营过渡到自动化；扩建后容量真实变化；系统可通过模拟测试完成 MVP 胜利条件。  
**不做：** 无限声望转生、连锁酒店城市地图。

## 批次 E — 三维酒店与世界表现

### HYA-010 — 模块化建筑、楼层和客房装配（P0 / M）

**依赖：** HYA-002，且已定义 HYA-004 房型/楼层接口。  
**范围：** 大堂、标准房、豪华房、层板、电梯、走廊的重复模块；4 层上限的 MVP 组装；可复用家具、贴图与视觉升级槽位。  
**验收：** 扩建时建筑真实长高/增加房间；多房间复用不会线性产生不必要的新材质、光源和 Draw Calls。  
**不做：** 先做 30 个不同的高模房间。

### HYA-011 — 房态与 3D 场景事件桥接（P0 / M）

**依赖：** HYA-005、HYA-010。  
**范围：** 状态事件→房门/灯光/客房布置/清洁车/入住标识/浮动收入反馈；Raycast 点击房间展示真状态；不通过渲染改变模拟器。  
**验收：** 用预置种子脚本触发入住、退房、清洁和升级时，可在 3D 看见相符变化；点击区域不串房；UI 显示同一状态源。

### HYA-012 — 角色池、动画复用及 LOD（P0 / M）

**依赖：** HYA-002、HYA-011。  
**范围：** 近景少量骨骼 / 中景简模 / 远景 Sprite 的角色三级表示；固定导航点、排队、入住、离店、清洁、前台工作动作；可见角色数限额。  
**验收：** 角色移动自然、状态与业务事件对应；镜头远近切换无明显跳变；100 个模拟客人不要求绘制 100 个完整 3D 人物；可配置密度并有测量数据。  
**不做：** 每名人物完整 AI 寻路与独立高面数骨骼模型。

## 批次 F — 玩家界面与体验

### HYA-013 — 统一 HUD、升级面板和反馈提示（P0 / M）

**依赖：** HYA-006、HYA-011。  
**范围：** 顶部 Cash/收入速率/声望/房态/评级；左侧当前目标；右侧统一升级抽屉；底部下一项推荐升级；升级详情显示价格、当前→升级后、效果与不可用原因。  
**验收：** UI 不能出现多抽屉重叠；所有数字来源于状态选择器；桌面 HUD 不遮挡关键房间；升级失败提示有实际原因。  
**不做：** 多套风格并存或工具栏菜单无限堆叠。

### HYA-014 — iPhone Safari 触屏/横竖屏与输入容错（P0 / M）

**依赖：** HYA-013。  
**范围：** 横屏主布局，竖屏压缩 HUD；安全区、双指缩放、单指有限平移、点击代理碰撞体；最小触控目标、字体缩放、失焦恢复、加载失败重试。  
**验收：** 横竖屏均可完成核心操作，菜单无屏幕外不可点击项；无 hover-only 操作；触控与 3D 点击不冲突。  
**注明：** 若无法使用真实 iPhone，只能完成桌面响应式模拟验证，并列出未完成实机验收。

### HYA-015 — 新手引导、里程碑、30 分钟终局（P1 / M）

**依赖：** HYA-007、HYA-009、HYA-013。  
**范围：** 只引导第一次订单、第一次购买、第一次自动化、第一次扩建；引导可跳过；阶段目标；达成后结果页并允许重新开始。  
**验收：** 新玩家不看 README 也能完成首单与首次升级；Demo 具有明确可达终点；结算页记录所用游戏时间、主要升级、收入曲线。  
**不做：** 长文本剧情、第二酒店、多人排名。

## 批次 G — 性能门禁、发布与验证

### HYA-016 — 最繁忙场景的真机性能与图形优化（P0 / L）

**依赖：** HYA-010 至 HYA-015 完成可玩整合。  
**范围：** 构造 ≥4 层、24 间可视房、多人同时进出/清洁、升级抽屉打开、收入特效触发的固定 worst-case；优化光照、角色、instancing、贴图、分辨率、资源总量；提供自动质量降级。  
**验收：** 目标 iPhone Safari **实机**连续 15 分钟平均 ≥30 FPS，且不得连续 3 秒低于 25 FPS；保留 P50/P95、Draw Calls、真实机型、系统版本、画质档与热稳定记录；未测标记 `MOBILE_PERF_UNVERIFIED`，不以桌面代替。  
**不做：** 靠删除核心玩法逻辑虚假提高帧率。

### HYA-017 — 自动化回归测试、预览部署与故障恢复（P0 / M）

**依赖：** HYA-014、HYA-015。  
**范围：** Playwright E2E、单元测试与生产构建 CI；测试上下文丢失、加载失败、存读档、升级、双订单和终局；GitHub Pages / 静态预览部署按用户现有仓库策略设定。  
**验收：** PR 自动检查全绿；可分享 HTTPS URL 正常加载 3D；随机种子复现问题；错误日志不暴露敏感数据。  
**不做：** 未检查的自动合并和发布到应用商店。

### HYA-018 — 外部玩家试玩与迭代决策报告（P1 / M）

**依赖：** HYA-017、关键性能门禁有记录。  
**范围：** 给 20–30 位目标玩家进行非强制试玩的测试说明、匿名行为记录/访谈表、首分钟理解率、首项自动化到达率、各阶段掉线点、继续游玩/付费意愿；需要获得合适同意，不擅自上传个人标识信息。  
**验收：** 将数值问题、UI 问题、画面问题分开优先级；提出继续开发 3–5 小时正式版 / 重做核心循环 / 停止投入的 Go/No-go 决策依据。  
**不做：** Work 自动伪造玩家测试结论。

**PR 拆分规则：** 一张 Ticket 对应一份主要 PR；单项工作超过约 300–500 行核心逻辑变化时可以拆成多个更小 PR。不要在一个 PR 里同时推导模拟器、重写 UI、重建 3D 和加入资产管线。

## 3. Sol / Work 的执行守则

1. 先读取三份 Markdown（游戏定调、开发计划、Tickets）；如有冲突，以最新用户明确决策为准，并在 PR 标注差异。
2. 先检查真实仓库状态、已有 PR 和 CI；不重复实现已完成任务，不覆盖并行工作。
3. 每批只做约 1–3 张 Tickets；按依赖拓扑顺序推进；每次以可审核、可运行的 PR 为交付物。
4. 可独立做合理、可逆的技术选择；未知商业化事项留作后续议题，不阻断渲染/经济原型。
5. 无法在 Work 中触达 iPhone 真机时，提交浏览器可执行的性能采集界面和用户真机操作说明，并明确注明未验收。
6. 不能以截图、美术示意图或占位图冒充实时运行的 Three.js 游戏。
7. 不能从旧网页的 minified bundle 修改经营系统，也不要移植未审核商用权利的真实酒店素材。
8. 每张 Ticket 的测试结果、截图、性能证据与阻塞原因必须入 PR；保留恢复与回滚路径。
9. 不自行合并 PR，完成后提交 PR 链接、验收结果与下一批建议。
