# HEYAT HOTEL｜技术架构与开发实施计划

> 版本：V0.9（执行基线）  
> 日期：2026-10-22  
> 目标技术栈：TypeScript + Vite + Three.js + WebGL 2（以 `WebGLRenderer` 为主）  
> 项目地址：`GarronMeng/HEYAT`（私有、默认 `main`；文档导入时仓库已由 README 引导初始化，尚无游戏源码）  
> 交付优先级：核心经营可玩 > 设备流畅 > 视觉精修 > 内容扩展。

## 0. 工程原则与仓库状态

1. `HEYAT` 是独立新项目，禁止直接在旧《今晚有套吗？》GitHub Pages 的压缩 bundle 上开发。
2. 旧预览在 `GarronMeng/GarronMeng.github.io/games/jinwan-youtao-v8-preview/`；其 `index.html` 引用哈希命名构建资源。可维护源码尚未核实，只有定位源码并确认复用价值/授权后才允许移植模块。
3. 仓库已通过 README 引导初始化，游戏工程尚未建立：**先初始化项目、CI 与开发环境**，所有实现通过 feature branch → PR → 自动检查 → 合并。
4. 游戏模拟器、存档、配置、UI、Three.js 渲染严格分层；绝不允许渲染回调直接修改现金或客房状态。
5. 不能承诺所有 iPhone 均达到相同 FPS。必须以定义的目标设备和最繁忙场景通过性能门禁；不达标不得宣布优化完成。

## 1. 技术决策（有意收敛范围）

| 层 | 选择 | 原因 |
|---|---|---|
| 语言 / 工具链 | TypeScript + Vite | 构建轻量，适合快速迭代 |
| 3D | Three.js `WebGLRenderer`, WebGL 2 优先 | 满足已选技术条件，桌面/手机同源 |
| 数据状态 | 独立 `GameState` + reducer/commands | 经济与 UI/3D 一致，便于重放测试 |
| 模拟时钟 | 固定时间步（建议 100–250ms） | 避免 FPS 变化改变经营收益 |
| UI | HTML/CSS UI 覆盖于 canvas（可用轻量框架） | 字体清楚、适配手机、易于测试 |
| 美术资产 | `.glb`/glTF + 共享材质、烘焙贴图；KTX2 可选 | 易于模块化和压缩 |
| 存档 | 本地 IndexedDB（或精简版 localStorage）+ schema version | 刷新安全，支持存档迁移 |
| 测试 | Vitest + Playwright + 设备实机测试 | 单元、端到端与 WebGL 联合验证 |
| 部署 | GitHub Pages / 静态 HTTPS 预览，后续 Steam 包装评估 | 避免服务器依赖 |

**禁用外部运行时 Three.js CDN 作为生产唯一依赖。** 依赖须由构建打包、锁定版本。尽量不用任意高开销后处理、实时 GI、复杂碰撞物理。

## 3. 游戏系统实现：可维护性优先

### 3.1 事实状态与指令

`GameState` 至少包含：版本、游戏时间、随机种子、余额、声望、楼层、客房、客人队列聚合、升级等级、里程碑、事件序列号、最近结算时间。

所有玩家操作使用显式命令：`CHECK_IN_GUEST`、`START_CLEANING`、`BUY_UPGRADE`、`BUILD_ROOM`、`UNLOCK_FLOOR`、`SET_PRICING_POLICY` 等。命令返回成功/失败及原因，UI 必须准确展示。

### 3.2 房态与客流

客房状态机：

`LOCKED → AVAILABLE → RESERVED → OCCUPIED → DIRTY → CLEANING → AVAILABLE`。

- 抵达事件生成客人需求，前台处理队列，空房与房型匹配，入住开始占房，退房后需清洁。
- 大堂角色是经营事件的**视觉表现**，不是经济状态源；视觉角色可以少于模拟客人总数。
- 队列长度有上限，超出统计为流失客流。无空房时不进入不一致的半入住状态。
- 每个订单由唯一 ID 结算一次；游戏刷新/恢复/多次点击都不会重复付款。
- 暂时不做复杂寻路：固定导航点 + 曲线/插值移动 + 动画状态机即可。

### 3.3 数值系统

用统一配置定义升级：`id, branch, maxLevel, costCurve, effects, unlockConditions, visualChanges`。

示意计算：

- `cost(level) = baseCost × growthFactor^level`（真实配置允许分支差异）；
- 升级并非全部 `income ×1.1`，部分直接开启自动操作、更改队列和房态时长；
- 以实际订单和房态事件作为现金结算，不用 UI 显示的每分钟预测值直接加钱。

进行多种购买策略的离线批量模拟，检查：升级可达性、前 5 分钟自动化、15 分钟扩建、30 分钟通关、长期不溢出、无死循环和无收益为负。UI 上的 `现金/分钟` 是滚动统计或平滑估算，必须与实际累积现金可解释地一致。

### 3.4 游戏节奏

- 0–5 分钟：1 间客房 → 经营第一笔收益 → 自动入住。
- 5–15 分钟：更多客房、自动清洁、分支升级。
- 15–30 分钟：完成关键扩建与原型终局。
- 超过 90 秒没有可做的有意义决策需列为节奏问题，避免靠等待人为延长游戏时长。
- 首个版本不做离线收益、多人在线、广告或完整转生系统。

## 4. Three.js / WebGL 2 实现约束

### 4.1 场景与相机

- 以剖面模块化建筑为中心：预制一个 `floor` 与多种 `room`，拼装组合，并记录几何、材质与碰撞代理。
- 锁定 3/4 角度，限制左右旋转范围，缩放时按距离选择显示细节；不允许自由飞行使模型背面露馅。
- 多人同屏仅在可见楼层内抽样：关键 3D 骨骼角色 + 中景低复杂度模型 + 远景 Sprite。
- 客房、家具、行李箱及植物优先共享几何与材质，用 instancing / batch 降低 Draw Calls。
- 透明玻璃最小化重复叠加，尽量避免多层透明叠绘；使用贴图模拟反射。

### 4.2 灯光与材质

- 房间主光照通过 baked lightmap / 预烘焙贴图或经过验证的等效方案实现，实时光用于极少数关键反馈。
- 默认不启用全场景逐灯实时阴影、镜面真实反射、重度 SSAO、全屏 Bloom 多 pass 堆叠。
- 避免为每个房间使用独立实时阴影灯；夜景窗外用低成本背景层、假反射与可控发光材质。
- glTF 批量优化；共享纹理图集、mipmaps；通过 KTX2/Basis 评估显存与下载量降低。

### 4.3 模型与人物预算（初始规划，须实测修订）

| 指标 | 手机预设目标 | 桌面预设目标 |
|---|---:|---:|
| 目标帧率 | 持续 ≥30 FPS | 持续 ≥60 FPS |
| 同屏核心骨骼角色 | 4–8 | 15–25 |
| 同屏其他简化 3D 角色 | 8–15 | 30–50 |
| 远景 Sprite / 贴图人群 | 20–40 | 50–100 |
| Draw Calls | 尽量 ≤150 | 尽量 ≤300 |
| 3D 三角面预算（可见场景） | 初始 20–40 万 | 初始 60–120 万 |
| 渲染分辨率倍率 | 动态 0.75–1.25 | 动态 1.0–1.5 |

**这些是探索期的上限起点，不是达标的充分条件。** 高频透明、过度绘制、纹理显存、shader、CPU 逻辑或发热都可能提前触及瓶颈。高端桌面与旧 iPhone 不应套用同一档画质。

### 4.4 质量分档与降级顺序

- **High**：桌面高画质，更多角色和局部特效；
- **Medium**：手机默认，30 FPS 目标，轻度粒子和限制角色；
- **Low**：减小内部渲染分辨率、关闭非必要后处理、压缩角色/粒子数量；
- **Fallback**：WebGL 初始化失败或环境不支持时，提供解释、重试及简化画面/经营信息，不得白屏。

降级顺序：非关键后处理 → 阴影/灯光效果 → 角色远景细节与数量 → 背景装饰 → 内部渲染分辨率；**最后才考虑降低核心可交互内容可见性**。所有画质档共用同一个模拟器与存档。

### 4.5 WebGL 生命周期

处理 `webglcontextlost` / `webglcontextrestored`；页面失焦与重回前台时停止/恢复渲染时钟，模拟时钟不得因为浏览器后台时间差而暴增收益；音频需用户手势后启动。资源加载支持超时、错误和重试。避免手机浏览器依赖不可控的第三方 CDN。

## 5. 性能门禁（硬性验收，不以概念图推定）

### 5.1 最早启动的性能原型

在完整经营系统前，先制作**1 个酒店大堂 + 2 个可售客房 + 6 个动态角色**，加载真实的目标纹理和灯光风格。随后建立最坏场景：至少 4 层、24 间可视客房、多种房态变化、前台队列、清洁人员、收入特效、升级 UI 同时存在。

### 5.2 目标测试设备与场景

- 手机基线：至少一台 **iPhone 12 / 13 级别**设备的 Safari（需真实设备）；更老设备可进入 Low 画质。
- 桌面：普通集成显卡笔记本的 Chrome；不只在高性能独立显卡上测试。
- 热启动场景：进入游戏后 15 分钟连续高负载经营（检查发热和性能下降）。
- 最坏场景：最高楼层、多人同时入住/清洁/退房、升级面板打开、音效和可见特效同时触发。
- 横屏与竖屏都测试输入、遮挡和安全区；重点视觉体验优化横屏。

### 5.3 发布闸门（暂定）

1. 手机目标设备高负载持续 15 分钟，**平均 FPS ≥30**；不得出现连续超过 3 秒低于 25 FPS 的严重卡顿；同时记录帧时间分位数（P50/P95）而非只看平均值。
2. 桌面基线平均 FPS ≥60；若硬件不支持，则主动记录机型与限制，不冒称全平台保证。
3. 手机 Draw Calls 优先压到 150 以下，超预算时需要报告原因与重测数据。
4. 无持续增长的内存占用、无 WebGL context loss 导致不可恢复白屏、无严重资源加载失败。
5. 视觉降级只影响效果，不影响订单、现金、房态、存档或点击命中。
6. 任何版本若没有完成实机测试，应标注为 **性能未验收**，不得写作“iPhone 流畅运行已保证”。

参考：MDN《WebGL best practices》、Three.js `InstancedMesh`、`WebGLRenderer` 与响应式渲染官方文档。

## 6. 工程质量、测试与 CI

### 6.1 必需的自动化测试

- [ ] 同一房间不可同时存在两个未结束订单。
- [ ] `DIRTY` 房间不可出售，清洁后才变 `AVAILABLE`。
- [ ] 资金不足不可购买；购买原子化，不能重复扣款/重复升级。
- [ ] 手动与自动入住不能对同一客人重复结算。
- [ ] 后台标签页、页面刷新、重启后时间与收益一致。
- [ ] 存档版本升级可迁移，异常存档有明确恢复路径。
- [ ] 经济模拟 30 分钟能达到目标，不发生升级死锁 / NaN / Infinity。
- [ ] WebGL 加载失败、失去上下文、网络中断有可操作错误信息。
- [ ] 购买升级会同步更新 3D 表现与 HUD，不存在 UI 显示成功而核心状态未更新。

### 6.2 开发管线

每个 PR 必须通过 `lint`、`typecheck`、`unit-test`、`build`；里程碑阶段另跑 `e2e` 与浏览器截图回归。大型 `.glb` 与贴图应受总下载体积预算约束，发现构建输出异常增长即提示。对图形性能数据建档（设备/版本/质量档/分辨率/平均 FPS/P95/Draw Calls/显存估计）。

## 7. 六周开发与验收

| 阶段 | 任务 | 交付物及通过标准 |
|---|---|---|
| W1：基础与性能原型 | 初始化 HEYAT 仓库、配置 TypeScript/Vite/CI，建立状态机与经济模拟；跑首个大堂+2 房+6 人渲染基准 | 可启动网页；核心单测；首份真实移动端性能记录，验证视觉路径可行 |

| W3：模块化酒店 3D | 可扩建建筑、房间房态与灯光动画、人物 LOD/路径动画、点击房间 | 玩家的经营状态可在 3D 场景中观察；可扩成 4 层 |
| W4：完整前端 | 顶部 HUD、可折叠升级面板、目标/推荐升级、触屏/横竖屏适配、音效与反馈 | 桌面和手机都能完整操作，无重叠/遮挡和输入失效 |
| W5：性能 + 稳定 | 最坏场景压力测试、资源压缩、自动画质分档、存档迁移、浏览器异常 | 目标设备通过 15 分钟性能门禁；CI 和关键 E2E 通过 |
| W6：玩家验证 | 20–30 位外部目标玩家测试，调整数值节奏、文案与视觉反馈 | 输出留存/阻塞/升级理解/购买意愿测试记录，决策是否开发完整 3–5 小时版本 |

**关键依赖：** 如果 W1 目标手机性能基线已失败，不得继续增加模型细节；先修渲染架构和质量分档。如果 W2 核心循环不好玩，不得用 W3 的视觉效果掩盖问题。

## 8. 每阶段 PR 建议

- `chore/bootstrap`: 初始化 Vite/TS/Three.js、README、CI、lint/typecheck/test。
- `feat/sim-room-lifecycle`: 房态机、命令和单测。
- `feat/economy-progression`: 升级、费用曲线、里程碑与模拟器。
- `feat/save`: 保存、恢复、迁移。
- `feat/scene-diorama`: 模块化大堂、房间、相机。
- `feat/characters`: 小人角色 LOD、事件映射和动画。
- `feat/ui`: HUD、升级抽屉、响应式布局。
- `perf/mobile`: KTX2/贴图、InstancedMesh、质量分档、基准数据。
- `test/vertical-slice`: E2E、压力测试、正式演示构建。

所有 PR 小步合并，不建立大型难审查的总分支；默认不直接改 `main`。

## 9. 第一个开发指令（供 Codex / Opus 使用）

> 请在 `GarronMeng/HEYAT` 初始化全新、可维护的 TypeScript + Vite + Three.js WebGL 2 项目。首先读取 `docs/HEYAT_GAME_VISION.md` 与 `docs/HEYAT_DEVELOPMENT_PLAN.md`。只完成 W1：构建工程、开发确定性模拟器骨架、房态机与测试，并搭建一个能显示大堂+2间客房+6名低复杂度角色的性能基准场景。必须内置 FPS、帧时间、Draw Calls、三角面数诊断信息，支持手机 Quality Low/Medium/High 切换，并在 iPhone Safari 中验证 WebGL 加载、操作、缩放和连续性能。不需要复制旧项目编译后的 JS，不要直接在旧项目上改动，不要增加多酒店、付费、广告、在线账户或复杂人员 AI。通过 PR 提交，附设备实测记录、截图及尚未通过的门禁；未经实机测试不得声称达到稳定 30 FPS。
